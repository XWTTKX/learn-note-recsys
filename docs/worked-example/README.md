# 图解案例：为什么同一个推荐模型能从 0.00004 变成 0.589

这章从一条三候选的教学请求开始，再到真实 Qilin toy 的本地记录。先区分「候选是谁给的」，再定位 ItemCF 是没有机会、没有信号，还是把正例排得太后。

```text
                           测试请求
                              │
       ┌──────────────────────┴──────────────────────┐
       │                                             │
从训练期目录找候选                         直接用旧系统的曝光候选
检索和排序一起算                           只在给定小池里做重排
候选可能没有点击正例                       正例通常已经在这个池里
       │                                             │
       └──────────────────────┬──────────────────────┘
                              ▼
                 计同一个指标，但回答不同问题
```

## 第一步：先从一条记录里看出边界

| 训练请求 | 用户 | 点击笔记 | 曝光但未点 |
|---|---|---|---|
| t1 | u1 | A、B | D |
| t2 | u2 | A | D |
| t3 | u3 | B | D |

测试 u4 的历史是 [A]，旧策略展示 [B,C,D]，其中 B、C 点击，D 未点击。目录由训练曝光构成 {A,B,D}；移除已看 A 后，能够比较的是 {B,D}。C 没进目录，再好的精排也无法把它排到第一。

A 和 B 共有 u1，一个用户看过两条，权重为 1/log₂(4)=0.5；A、B 的受众都是 2，协同值 0.25。排序因此将 B 放到 D 之前。B 在任一协议下都能进前列；C 在日志模式可参与打分，但模型没有为它学到协同分。K=2 时 C 和 D 都是零分，最终代码按 ID 打破平局，把 C 放在 D 之前。注意：**命中这一条 C 不是学会了冷启动；可以改它的 ID 验证同分因素。**

```python
import sys
sys.path.insert(0, "scripts")
from metrics import metrics
from recommender import Recommender

def request(user, positives):
    return {
        "user": user,
        "candidates": [{"id": item, "click": 1} for item in positives]
        + [{"id": "D", "click": 0}],
    }

model = Recommender([request("u1", ["A", "B"]), request("u2", ["A"]), request("u3", ["B"])])
correct = {"B", "C"}
cases = {
    "catalog": model.rank(["A"], method="itemcf", k=2),
    "logged": model.rank(["A"], ["B", "C", "D"], method="itemcf", k=2, filter_seen=False),
}
print("similarity A→B", model.sim["A"]["B"])
for protocol, ids in cases.items():
    print(protocol, ids, metrics(ids, correct, k=2))
```

预期目录 [B,D]、Recall@2=0.5；日志池 [B,C]、Recall@2=1。分别做两个小实验：

- 只把 K 改成 1：日志池本来能放两个正例，现在只能展示一个。候选覆盖没有变化，不要把下降归因于采样。
- 把所有测试中的 C 换成 Z，候选与正例一起替换：日志模式 [B,D]。模型训练数据不变，分析「零分候选依赖 tie-break」比分析模型超参更有说服力。

## 第二步：先找每条请求的「上限」

记正例为 G、过滤后的目录为 C。某条请求至少漏掉 G−C 的项目，且只能展示 K 条。它的最好 Recall 为：

$$
\frac{\min(K, |G\cap C|)}{|G|}.
$$

举例，某请求有 4 个正例，其中 3 个在库里，K=2 时最多命中 2 个，上限为 1/2。若只统计 OOV，得到 3/4，忽略了展示数量。对全部请求先算每条的比值再平均，就是宏上限；先合计可命中数量再算比值，就是微上限。正例为空的请求不能除以 0，应该记排除数量并另行分析。

<details>
<summary>练习：两个请求的上限相差很多，哪种平均更公平？</summary>

取决于目标。宏平均按每个请求同样加权；微平均按每个正例同样加权，正例多的请求权重更大。给用户的首页每次刷新同等重要时，宏平均更易解释。最好明确报告口径及样本量，避免比较口径混淆。
</details>

## 第三步：复现一个不漂亮、但有价值的真实诊断

先按 [运行章](../06-quickstart/README.md) 转换公开 Qilin toy。然后执行：

```bash
python3 scripts/coverage_lab.py --data data/processed/qilin-toy.jsonl --k 5
```

这个脚本只求目录交集和历史覆盖，不必在每次请求都完整排序，多数时候比同目录跑 demo 更适合先诊断。项目 [验证记录](../../experiments/VALIDATION.md) 中，该文件转换得到 10,767 请求，使用 3,231 条测试请求；下表为同一套本地切分的数值，四舍五入：

| 观察 | 数值 | 应该怎么读 |
|---|---:|---|
| 正例不在训练目录的比例 | 67.56% | 覆盖丢失，不是精排错误 |
| 宏 Recall@5 理论上限 | 29.11% | 用 K 与每条请求的正例数计算 |
| 有至少一个图邻接种子的请求 | 82.54% | 只说明有可用线索，不说明能连到正例 |
| ItemCF 全目录 Recall@5 | 0.000039 | 该口径下弱于热门 |
| ItemCF 日志候选 Recall@5 | 0.58910 | 旧系统给定候选，不是端到端指标 |

这不是官方完整 benchmark，也不代表线上系统。如果只看最后一行，你可能误判算法效果已经很好；如果只看上限，你又可能低估模型与排序的其他问题。把两者并列才能解释接下来该做什么。

## 第四步：从诊断树决定改动

```text
这条正例在请求时可用吗？
  ├─ 否 → 核对目录快照、内容发布时间、ID 类型
  └─ 是 → 当前候选路含它吗？
           ├─ 否 → 查历史图邻接；试内容召回、增量索引
           └─ 是 → 它是否在展示 TopK？
                    ├─ 否 → 看分数、同分、规则与截断
                    └─ 是 → 看位置、多样性及用户反馈口径
```

这里的「可用目录」不等同于「最终候选池」。在纯目录基线里两者可很接近；多路服务中，目录只是允许服务的商品总表，候选池是多路选中的子集。若服务使用下架过滤、历史去重或同作者约束，也要把过滤前和过滤后分别记录。

### 写进面试项目的实验设计

先冻结训练切分和基线，再控制两个变量：(1) 固定策略只改**请求时已发布**的合法目录，报告宏上限与真实指标；(2) 固定目录只改候选或排序，看每路独有命中、前 K 和延时。选择一条缺目录、一条无邻接、一条候选排后的请求做回放，报告各类数量；试过不奏效也写出原因。这里不建议直接加一个更大的神经模型，因为没有诊断支持具体要解决的问题。

<details>
<summary>自查：同一个模型的 0.589 与 0.00004，可以相减得到提升吗？</summary>

不可以。它们对应不同候选集；0.589 中正例已被日志候选的选择机制带进池。想比较两个策略的提升，先固定候选、训练与测试口径。想比较资源改善，再固定策略、单独变化可服务的目录，并同时报告它带来的额外候选量。
</details>
