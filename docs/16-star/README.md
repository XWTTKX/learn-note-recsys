# 16 · 项目陈述与失败复盘

## 90 秒怎么讲一个结果不理想的项目

场景：我想在公开笔记日志上判断推荐链路哪里最先出问题。任务：先构建可比较的基线，不依赖外部 GPU。我按请求时间切开训练和测试，把热门与 ItemCF 放在两种候选协议下跑。结果发现不少正例在训练目录里不存在，日志内指标却很高。于是我再加目录上限诊断，拆出真正的覆盖差距与排序差距。当前 toy 版本的全目录 ItemCF 没超过热门，所以优先补近期内容和覆盖，再看更复杂的模型。

追问时自然衔接：当对方问「你为什么没上双塔」，说明向量模型不可能从一个不存在的目录召回新笔记；先明确内容可用性，再在同口径对照下判断双塔值不值得。不要把设计线路当已跑完的成果。

## 90秒结构

问题：笔记内容多、用户兴趣变化，单一热门推荐不够个性化。数据：使用公开Qilin或明确声明的样例。方案：先热门/ItemCF，再逐步加双塔与排序；已经做到哪一步就说哪一步。评测：区分全库召回和日志候选重排，避免把候选选择的信息泄漏到召回评价。结果：给实测值与局限。

## 一个可练习的复盘题

发现召回率很高后，检查是否只在曝光候选里排序。任务是建立统一评价口径；行动是显式候选池、移除测试标签依赖、报告新物品OOV；结果是得到更可信但可能更低的指标。只有你实际完成过这个检查，才能作为自己的STAR经历。

## 深挖路线

“为什么选这些模型？”→ 从基线错误与资源约束解释。

“哪里是你的工作？”→ 指向自己实现的数据适配、评测、实验与修复；上游模型明确归属。

“上线会遇到什么？”→ 特征缺失、索引过期、延迟超时、流量偏移，结合一条实际故障演练回答。

“改动没提升怎么办？”→ 检查训练和验证一致性、统计不确定性和分桶结果，再决定保留基线或调整假设。失败实验也应可复现。
