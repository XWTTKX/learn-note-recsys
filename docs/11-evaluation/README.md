# 11 · 全库召回、候选重排与偏差

## 为什么同一个推荐器能跑出两套差很多的数字

[验证记录](../../experiments/VALIDATION.md)来自 Qilin toy，训练期出现过约 7 万条笔记，时间顺序切分后跑同一个 ItemCF。目录模式 Recall@5 约 0.000039，日志内候选模式约 0.5891。两者任务不同：目录模式要从训练曝光目录里找未来会点击的笔记；日志模式已经给定当时有曝光的候选，正例基本就在这组候选里。前者同时考察目录覆盖、召回和排序，后者只描述在旧策略选出的候选里如何重排，不是一次算法迭代带来的涨幅。

目录模式的有效正例里约 67.56% 不在训练目录；这表示按合计正例求的理论可达 Recall 上限约 32.44%，还没计入 K 截断。实际输出是逐请求宏平均，宏上限要逐请求计算 $\min(K,|G_q\cap C_q|)/|G_q|$ 再平均，不能直接用 32.44% 当宏上限。此审计中，ItemCF 在目录模式下还弱于热门；合理下一步是查目录覆盖、历史邻接率和热门回退，不能包装成「个性化带来提升」。

## 手算两个候选口径

请求正例是 A、C，只有 A 出现在训练目录。目录结果为 [B,A]，K=2，Recall=1/2，NDCG=$0.6309/1.6309\approx0.387$。日志候选是 [A,C,B]，如果排序输出 [A,C]，两指标都为 1。这里 C 的未覆盖应在目录模式保留在分母，明确说明召回失败；若把它丢掉，实际上改成了「仅在可召回正例上计算」。两种都可报告，但要分别命名。项目对目录模式还会过滤已在历史中的笔记，并同步从正例移除；若线上业务允许继续阅读，需取消这项策略并重定口径。

## 从离线结果到下一步

| 表现 | 优先诊断 |
|---|---|
| 候选覆盖低 | 候选目录的时效、OOV、新笔记比例 |
| 覆盖高但 Recall 低 | 计算命中位置、候选 K 和各路分布 |
| Recall 上升但 NDCG 下降 | 新增正例有多少排在末尾，是否牺牲前几名 |
| 日志评测好但业务表现差 | 日志采样政策、位置、流量来源、线上实验 |
| 总体相近但长尾掉很多 | 报告分组样本量和配对差，不能按总体掩盖 |

离线日志只观察被曝光项的反馈；即使同时看到点击率和 NDCG 升高，也不能外推新策略让用户体验提升。要估计位置倾向需要相应观测（如有控制的曝光数据或可靠的倾向估计），并检查覆盖假设，不能凭位置序号任意加权。真正 A/B 要预定义主指标、守护指标、实验单元和观察窗；做到离线实验即可如实写入个人项目。

练习：全局 AUC 高是否意味着每个用户都排得好？把两个用户的所有分数分别整体抬高和压低，跨用户正负比较会变化，但每个用户内部顺序一点没变。可另报每请求有两类标签的 AUC 或 NDCG，并说明不可计算请求如何处理。

这是最重要的一章。**在给定曝光候选里找点击笔记，不等于从整个内容库里召回点击笔记。** 两者的候选难度、可用信息和指标分母不同，结果不能放在同一列比较。

当前demo明确输出：

- `full-train-catalog`：从训练中出现过的物品集合检索；过滤历史看过项，正例也按同一策略处理。测试新物品不在库内仍计入分母，并报告positive_oov_rate。这不等于Qilin约百万内容全库检索。
- `logged-candidates`：只排序该请求日志候选，不滤历史项，以保持给定候选池。这个结果是条件重排质量，不是端到端召回率。

Recall分母是该请求有效正例数；HitRate只判断有没有命中；NDCG衡量位置。没有正例的请求在当前指标中排除并报告数量。排序AUC通常按曝光计算；GAUC应明确分组键与权重，单一标签组不能计算AUC，应报告排除比例。

## 常见虚高来源

把真值强行加回召回候选再计算Recall；测试点击加入ItemCF统计；把同请求拆入训练与测试；以曝光位置当推荐排序特征；只报告少量容易请求；用全量日志构建未来热门。

离线AUC提升不证明CTR提升。在线A/B需要随机分流、预设主指标与护栏、完整观测周期；没有线上环境时写出实验设计即可。随机曝光数据有助于偏差研究，但IPS仍需要支持重叠与正确倾向分数，且权重可能高方差。

验收：用同一模型跑两种协议并解释差异；提交一个故意泄漏与修复的对照实验，但只把修复后的结果作为成果。
