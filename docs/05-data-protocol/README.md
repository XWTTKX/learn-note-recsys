# 05 · Qilin字段、数据划分与泄漏防护

## 时间就是特征的权限边界

```text
11:49             12:00                  12:00:03            12:03
  │ 用户点 n2       │ 请求 r49，曝光 n8        │ 用户点 n8          │ 用户收藏 n8
  ├────────────────┼────────────────────────┴─────────────────┤
  │ 当时可读         │                   事后才能读
  │ history=[n2]   │ 点击 label=1；收藏要等归因窗口结束后写入
```

错误构造：把当天末尾的 history=[n2,n8] 放回 12:00 的训练样本。模型可以学「最近点击等于候选」这种捷径，线上不会出现。正确构造：按事件时间保留严格小于请求时间的历史，并把相同时间戳的边界规则写出来。若日志从多个数据源合并，不同系统时间可能有偏差；先检查时区、毫秒/秒和负时间差，不能把晚到的数据到达时间当事件时间。

## 从 CSV 字段追到标准请求

| 输入例子 | 转换 | 失败长什么样 |
|---|---|---|
| history 原始 ID 列是 JSON 数组 | 解析为序列，再把 ID 规范为字符串 | 混用索引 ID，历史与候选交集几乎为零 |
| candidates 是同请求的对象数组 | 取 note ID、click、事件时间，同 ID 合并 | 缺列或把 Python repr 当 JSON |
| UTC 秒或毫秒时间 | 核对原始定义后归一，再按请求聚合 | 年份跑到远未来、整个切分集中在一天 |
| 训练和测试两文件 | 校验请求 ID 交集与时限 | 顺序错误不会被显式测试入口自动发现 |

### 写给自己的一份最小数据审计

- 记下原始文件哈希、转换命令、输出请求数和丢失数。
- 从头、中、尾各抽几行，检查原始 ID 能否映射到同一请求，候选去重是否合理。
- 检查最早与最晚时间、边界两侧和并列时间；同一 request_id 不应跨两边。
- 比较正例在训练目录的比例，按日期分组找突然跳变。若切分前后直接使用不同 ID 字典，先修数据。
- 检查特征是否只能从请求以前重建；将任何不确认的字段先排除。数据切分是它之后的一道检查，不是全部。

<details>
<summary>练习：把昨天的点击作为今天测试请求的历史算泄漏吗？</summary>

不算，只要它确实已在请求前发生，而且在线同样能获取。训练与测试跨时间并不意味着必须清空用户历史。要防的是未来信息或把测试反馈用于模型拟合，而不是屏蔽合法的历史。
</details>

## 从原始日志构建一条可审查的样本

一条标准化请求可以是：

```json
{"request_id":"r49","user":"u7","timestamp":1700000000,"history":["n2","n9"],"candidates":[{"id":"n4","click":0},{"id":"n8","click":1}]}
```

这里的 `history` 是预测时的输入，`candidates.click` 是事后反馈。对于 n4，0 只表示这次记录中展示了却未点击，可能来自不感兴趣、没看到、停留窗口太短等情况。库里从未曝光的 n6 不具有同样的负标签；召回负采样可以取 n6，但应当把它称为抽样项。

[import_qilin.py](../../scripts/import_qilin.py) 负责把 Qilin 字段翻译成上面的结构：toy CSV 使用原始 ID 的成对字段，正式 parquet 的索引列走 `--indexed`。原始 ID 和索引 ID 是两个名字空间，即使都长得像整数也不能混用，否则 history 与候选可能永远匹配不到。曝光详情按同一请求的笔记 ID 合并，click 取 max，时间取详情最早的归一化时间。合并会丢曝光次数和位置，适合请求级候选排序，不适合直接估计位置偏差。该导入器面向可信数据和固定字段，生产化还需校验 0/1 输入类型与时间分布，并在整份成功后原子落盘。

## 切分并不自动保证无泄漏

按行随机切会使同一用户的未来点击参与过去评分，还可能把一个请求的候选拆到两侧。当前脚本按时间排序，找到目标分位的时间作为边界，同一时间戳全部留在边界一侧；因此比例可能不是恰好 70/30。如果全部时间戳相同，会因无法产生两个非空集合而报错。正式实验建议固定 train / validation / test 三个时间窗口，将调参限制在 validation，最终只用 test 做报告。

| 特征 | 正确快照 | 常见泄漏 |
|---|---|---|
| 用户最近点击序列 | 严格发生在请求前 | 包含目标点击或之后点击 |
| 笔记流行度 | 截至请求前的窗口计数 | 全量日志先聚合再切分 |
| 笔记内容向量 | 请求时已发布和可见的内容 | 使用测试期才发布的笔记快照 |
| ID 映射 | 稳定统一，未知值显式编码 | 把未知 ID 当成训练中第 0 个笔记 |

已有的历史字段也须审计产生方式；只按请求时间切分，不会自动清洗里面的事件时刻。显式 `--test` 模式下，当前 demo 不验证 `max(train_time) < min(test_time)`，按官方固定切分使用时另行记录边界检查，不要把它当防泄漏工具。

练习：同一个请求的两个候选时间为 1700000000123 和 1700000000323，重复笔记点击分别 0 和 1。归一化后请求时间取 1700000000.123，该候选最终为 1。若要保留两次独立曝光，就需要另建行级数据协议。

数据入口是 [THUIR/Qilin](https://huggingface.co/datasets/THUIR/Qilin)，包含推荐请求、历史和候选反馈。数据许可与上游代码许可分别记录；不把原始日志或笔记内容打包上传自己的GitHub。

## 已检查的样例CSV

`recent_clicked_note_ids` 与 `rec_result_details` 是可解析JSON；同文件的某些 `*_idxs`/`*_with_idx` 单元格呈NumPy风格字符串，不能直接json.loads。适配器默认使用成对的原始ID字段，绝不混用原始ID历史和整数索引候选。

统一输出为 `request_id,user,timestamp,history,candidates[{id,click}]`。同请求同笔记多次曝光暂按max(click)合并，时间取最早曝光；这是教学协议，会丢失位置与重复曝光信息。正式逐曝光CTR实验必须保留原始曝光键和时间。

## 防泄漏清单

1. 按请求或会话划分，不能把同一请求的不同候选随机分到train/test。
2. 历史来自请求前，不从“用户全部点击”反推测试历史。
3. 热门、共现、统计特征只用训练期；跨时间窗口统计须保存截止时间。
4. 验证集调参，测试集不做负例挖掘或超参选择。
5. 发布时间、曝光后互动统计、未来点击不能当请求时可知特征。

默认demo对样例按请求最早时间做70/30切分，不拆相同时间戳。该划分不是官方benchmark协议，且不保证会话完全隔离；正式复现保留官方split并额外审计会话交集。`--test`支持显式训练/测试输入，但仅检查request_id重叠，不会自动验证全部历史时间。
