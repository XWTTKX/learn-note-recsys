# 12 · 服务化、版本包与故障降级

## 检查一次版本发布和一次降级

产物包应有模型参数/相似度图、统一 ID 字典、候选目录、特征配置和生成时刻。发布分两步：先在隔离流量下加载并检查产物是否可读、索引和目录的 ID 是否匹配，再一次切换版本指针。旧版继续响应未完成请求。若只换索引后实际排序全走热门回退，可能是索引使用 note_idx、在线请求传 raw note_id。

| 故障场景 | 可用备选 | 同时观测 |
|---|---|---|
| 取不到用户历史 | 近期热门或内容分发 | 历史获取失败率、冷用户比例 |
| 某一路超时 | 用其余候选继续 | 每路超时、有效 K、候选重合 |
| 新笔记目录落后 | 查更新时间，用内容路补增量 | 配置版本、目录覆盖上限 |
| 用户过滤后候选不足 | 扩大候选或用备选池回填 | 比较过滤前后数量，不跳过硬性规则 |

不要把降级请求从整体延迟和质量监控里滤掉。记录生效策略及请求 ID，回放同一次请求能看出根因；恢复后跨版本缓存也要失效。该仓库是离线脚本，上述是设计演练，没有部署在线服务。

最小发布单元包括模型、词表、特征变换、内容向量、索引和manifest。manifest记录训练数据范围、索引构建时间、模型哈希和特征定义版本。在线请求拒绝混用不兼容版本。

特征从离线转到在线时应写一致性测试：同一请求的特征向量是否相同；缺失/OOV默认值是否相同；历史截断顺序是否一致。模型效果退化可能来自服务数据，而不是权重本身。

延迟按用户特征获取、召回、排序、重排拆开测。超时先减少低边际贡献召回路或候选量，再考虑缓存与模型压缩。排序不可用时保留候选顺序并标记降级；全链失败才热门兜底。

## 在线演示的验收产物

一个用户历史改变后的推荐对比；模型版本切换和回滚；缓存失效后仍能返回结果；一份真实压测报告。UI演示体现产品链路，算法能力主要由数据、训练与评价证据说明。

当前仓库CLI已可运行，FastAPI/Redis/Vue是上游阅读与后续扩展内容。不要引用第三方README的延迟数字作为自己的测量。
